# R0-05 Sign-in

Planned by the `planner` agent. The plan was followed, with the deviations listed under "Good to know".

## What was built
- **Laravel Fortify** (version 1.44), with only what we need: sign-in, sign-out and password reset. Registration, two-factor sign-in, passkeys and profile updates are switched off. Fortify's own addresses are switched off too, and ours are in `routes/web.php`:
  - `/members/sign-in`
  - `/members/sign-out` (POST only)
  - `/members/forgot-password`
  - `/members/reset-password/{token}`
  - `/members`: for signed-in members only. It is a placeholder that says "Welcome back" and has the sign-out button. The real overview is R1-14.
- **Members table:**
  - New fields: first name, last name, slug, institution, country, career stage (called "status" in the task), interests, ORCID, Discord name, directory visibility (default: not listed) and `approved_at`.
  - The framework's single `name` field is replaced by first and last name.
  - A member without a password (before activation) is allowed.
- **Who can sign in:** only users with `approved_at` set and a password. Everyone else, including an unknown address, gets the same answer as a wrong password: "The e-mail address or the password is not right." Nothing in the interface sets `approved_at` yet. That comes in R1-10 (approval) and R1-19 (import), and it cannot be set through a form by accident.
- **Lock:** after five failed attempts for one address from one IP, sign-in is locked for a minute, with the answer "Too many attempts. Please wait … seconds and try again."
- **Password reset:** every request gets the same answer: "Check your e-mail. If this address belongs to a member, a link to set a new password is on its way." That holds for a known address, an unknown one, an applicant who is not approved, and a repeated request. Only approved members get the e-mail.
  - The link is valid for 60 minutes and works once.
  - New passwords need at least eight characters, with the mockup's error texts.
  - Expired links are deleted every night by the scheduler.
- **E-mail** `PasswordResetLink`, with an HTML and a plain-text version. It holds the first name and the link, nothing else.
- E-mail addresses are stored in lower case, so sign-in works whatever capitals someone types.
- Wording from the mockup. No "remember me" box: the mockup has none, and only the session cookie may be set.

## How to see it
```
php artisan migrate
php artisan serve
```
Open http://localhost:8000/members. You are sent to sign-in. Test members come with R0-07. Until then, `php artisan tinker` with `User::factory()->create(['email' => 'me@example.test'])` makes one with the password "password". The reset e-mail is written to `storage/logs/laravel.log`.

## What was tested (27 new tests)
- Sign-in:
  - right password
  - wrong password
  - unknown address (same message)
  - not approved
  - no password
  - empty fields (mockup messages)
  - lock after five failures
  - capitals in the address
  - sign-out by POST only
  - a signed-in member is sent away from sign-in
  - the lock ends after the wait
  - no remember-me cookie, even when a request asks for one
  - a signed-in member is sent away from the reset pages too
  - expired reset links are cleared every day (scheduled)
  - `/register`, `/login` and the other Fortify addresses answer 404
- Reset:
  - the page wording
  - the e-mail is sent to a known address
  - an unknown address gets a byte-identical page and no e-mail
  - a throttled repeat gets the same answer
  - an unapproved applicant gets the same answer and no e-mail
  - an invalid address
  - the link sets the new password and the old one stops working
  - a short password and a mismatch
  - an invalid token and an expired token
- Member area: a guest is sent to sign-in, and a member sees the page.
- Data:
  - the directory default is "not listed"
  - `approved_at` cannot be set by mass assignment
- The e-mail:
  - it has an HTML and a text version
  - it holds the link and no profile data
- By hand, with JavaScript switched off: the wrong-password error and the "Check your e-mail" answer look right.

## What was not tested
- A real e-mail delivery. Locally the `log` mailer is used. Real delivery is R0-11.
- MySQL. The migration ran on SQLite only. It drops and adds columns, which MySQL supports.
- Screen readers. The errors are tied to their fields (`aria-describedby`, `aria-invalid`), but they have not been tried with a screen reader.

## Good to know
- **Texts not in the mockup**, written in its voice. Please check them, Tobi:
  - "Enter your password."
  - "The e-mail address or the password is not right."
  - "Too many attempts. Please wait … seconds and try again."
  - "Save the new password"
  - "This link has expired or was already used. Ask for a new one."
  - "Your new password is saved. Sign in with it."
  - the e-mail subject "Set a new password for the ERN member area" and its text
- **Reserved addresses** under `/members` that R1-13 (researcher pages, `/members/{slug}`) must never use as a slug: `sign-in`, `sign-out`, `forgot-password`, `reset-password`, `directory`, `profile`.
- E-mail verification (named in `docs/DECISIONS.md`) is not switched on yet. Nobody needs it before the e-mail change in R1-12.
- A member whose approval is later withdrawn stays signed in until their session ends. R1-10 should sign them out.
- The reset form is limited per address (one e-mail a minute), but not per IP address. A limit per IP would need our own route in front of Fortify's. Proposed for later.
- "Remember me" is refused on the server too: a hand-made request that asks for it gets only the session cookie (tested).
- The reset e-mail is sent while the request waits. On the hosting, sending takes some time, so a very careful observer could tell a member's address from an unknown one by measuring the answer time. To close this, send the e-mail through the database queue once the scheduler processes the queue (R0-08 adds the scheduled heartbeat; the queue run can be added there or in R0-11).
- Card headings are h2 instead of the mockup's h3, so the heading order is correct. They look the same.

## Ideas left out
- A rate limit per IP address on the reset form (see above).
