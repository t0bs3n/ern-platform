# R1-12 Profile

Planned by the `planner` agent and built as planned. One deviation: no separate policy class, because no address carries a member id. Every action works on the signed-in member, behind the new gate `use-member-area`.

## What was built
- **`/members/profile`, "My details"**, for every approved member, linked from the member area ("Update my details"):
  - **My details:** first and last name, university or organisation, country, "Status" (the career stage), research interests, ORCID iD (checked: four groups of four), Discord name.
  - **Visibility:** "Show me in the member directory", "I am open to collaboration requests", "Show my Discord name in the member directory". Every choice starts switched off, and an unticked box means "no".
  - "Save changes", then "Your details are saved."
- **What the directory shows (for R1-13):** when listed, it shows the name, career stage, institution, country, research interests and ORCID iD. The Discord name shows only with its own box. The e-mail address never shows.
- **A new name gets a new address name** (for example `maja-berg`), so a former name never stays in the page address.
- **Changing the e-mail address:**
  - It needs the current password.
  - A link goes to the new address only and works for 24 hours. Nothing changes until the member, signed in, opens it.
  - After confirming, the old address gets a notice that does not name the new one.
  - Old password-reset links are deleted, and the session is renewed.
  - If the new address is already taken, the answer is the same, the profile page looks the same ("Waiting for confirmation"), and no e-mail is sent. The e-mail is sent after the page has answered, so the answer takes as long for a taken address as for a free one. A failing e-mail clears the request silently. The member sees no "Waiting" line any more, and can try again.
  - A replaced, changed, expired or used link, or one opened by someone else, shows "This link is not valid or has expired."
  - Unconfirmed requests are forgotten after 24 hours by a nightly job.
- **"End my membership":**
  - A box to tick and "Send the request". An e-mail goes to each approved admin separately, with the member's name, address and "member since", and nothing more.
  - **Nothing is deleted:** not the account, the roles or the sessions. A second request within 24 hours sends nothing.
- **"Download my data":** a JSON file with everything stored about the member, including the date of their application and of their agreement. Never the password, internal numbers or who decided.
- **The new gate `use-member-area`:** every approved member passes it. The gate table and its tests were updated.

## What was tested (24 new tests)
- **Access:** all five addresses send a guest to sign-in and refuse an unapproved user, and nothing changes.
- **The page:** it shows the mockup wording and the member's own details. The "I am available as" boxes (marked as an idea in the mockup) are left out.
- **Saving:**
  - details and choices are saved, and an unticked box means "no"
  - wrong input (an empty name, a wrong ORCID iD, an unknown status, an overlong text) is refused with plain messages
- **Only their own profile:** sending another member's id, an e-mail address, the approval, an address name or a password changes nothing protected and no one else.
- **A new name** gets a new address name that avoids reserved ones.
- **E-mail change:**
  - it needs the password, and nothing changes until confirmed
  - the link goes to the new address only
  - confirming changes the address, deletes old reset links, and notifies the old address without naming the new one
  - the link works once
- **Refused links and addresses:**
  - a replaced, changed, borrowed or expired link
  - a taken address, with the same answer, the same profile page and no e-mail
  - a guest, an unapproved member, and a correctly signed link of another member
- **Session:** confirming renews it.
  - an address taken between request and confirmation
- **Failures and clean-up:**
  - a failing e-mail clears the request, gives the same answer, and logs no address
  - asking for the own address sends nothing
  - the nightly clean-up works and is scheduled
- **Ending the membership:**
  - it needs the box
  - it sends one e-mail to each approved admin and deletes nothing
  - once a day at most
  - the e-mail holds no profile details
  - a failure says so and sets nothing
- **The download:** a JSON file with the member's own data, no other member's data, and no password or internal numbers. It must not be stored by the browser.
- **By hand, at 375 pixels with JavaScript off:** saving, and no sideways scrolling.

## What was not tested
- Real e-mail delivery.
- Two members confirming the same new address at the very same moment: the database's unique address catches it, but only on MySQL is the timing real.
